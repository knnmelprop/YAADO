# FlightDeck

**FlightDeck** is the central orchestrator and "brain" of the YAADO framework. It takes the parsed vehicle geometry from `ComponentStore` and the physical calculations from `modules/`, and runs them through mission simulations and optimization loops.

## Sub-Domains
To keep the architecture clean, this directory is split into two distinct orchestration tasks:
1. **Mission Orchestration (SUAVE):** Uses SUAVE to "fly" the vehicle through a trajectory. It executes the mission by attaching high-fidelity surrogate maps (generated by our `modules/`) to the vehicle. Pretty much analysis workflows would be found here
2. **Optimization (OpenMDAO):** Wraps the mission orchestration in an optimization loop using OpenMDAO.

## Architectural Vision: The "Hidden OpenMDAO" Engine

The overarching philosophy of `FlightDeck` is to provide **world-class Multidisciplinary Design Optimization (MDO) without the steep learning curve.**

As of now, in the aerospace industry **OpenMDAO** is the undisputed industry standard for massive-scale optimization because of its use of analytic derivatives. However, it is notoriously complex and difficult for students to learn.

### Abstraction

My ([Arseni's](https://github.com/Arseni10Lk)) vision for `FlightDeck` is to use OpenMDAO as the underlying computational engine, but keep it **completely hidden from the end-user**. 

A person using YAADO should never have to manually define an OpenMDAO `Problem()`, manage `ExplicitComponent` blocks, or manually wire variables together using `connect()`. 

For example:
1. The user provides a declarative TOML configuration.
2. `FlightDeck` dynamically reads the `BaseVehicleConfig` and automatically translates it into an OpenMDAO tree in the background.
3. OpenMDAO optimizes the vehicle (adjusting wing spans, engine thrusts, and masses) using SUAVE as the mission evaluator.
4. The optimized parameters are returned to the user.

In short: **OpenMDAO provides the horsepower, SUAVE provides the pilot, and YAADO provides the steering wheel.**

## Launch Angle Optimizer

* **Module**: [`launch_angle_optimizer.py`](launch_angle_optimizer.py)
* **Status**: First OpenMDAO loop in FlightDeck.

`optimize_launch_angle(vehicle, ...)` finds the launch angle that maximizes the ground range of the 3-DOF point-mass flight (`PointMass3DOFBoostAnalysis` with `stop_at_burnout=False`). It returns a frozen `LaunchAngleOptimum` with the optimal angle, the maximum range and the number of simulations. The OpenMDAO `Problem` is hidden: the caller never builds one.

* One design variable (`launch_angle_deg`, default bounds 5-85 deg) and one objective (`flight_range`, maximized).
* The simulation has no analytic derivatives, so the component uses finite differences with a 0.5 deg step, and the driver is SciPy SLSQP. SLSQP needs fewer simulations than a gradient-free method such as COBYLA for one smooth variable.
* `om.Problem(reports=False)`: no `reports/` folder is written.
* Each simulation takes a few seconds, so a run takes about 20 simulations (a minute or two).

The optimum is flat: the range changes by less than 0.1% within about 1 deg of the optimum, so the angle is known to roughly 0.1 deg, not better.
