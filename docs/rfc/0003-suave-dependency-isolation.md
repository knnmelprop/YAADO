# RFC 0003 — SUAVE dependency isolation

**Status:** Draft / Request for Comments
**Related:** #29 (VehicleFactory), PR #33 (SUAVE integration notes)

> An RFC is a design proposal circulated for team feedback *before* implementation.

## 1. Problem

`VehicleFactory` (#29) needs SUAVE, but SUAVE 2.5.2 (the pinned `external/suave`
submodule) does **not** coexist cleanly with YAADO's modern, `uv`-locked
environment. The hands-on install in PR #33 (`docs/SUAVE_INTEGRATION_NOTES.md`)
established that a working `import SUAVE` requires:

1. `pip install --no-build-isolation -e external/suave/trunk` (SUAVE's `setup.py`
   eagerly `import numpy`s at build-requirement time).
2. **Three runtime shims applied before `import SUAVE`**, all on its eager import
   chain (so unavoidable), because SUAVE's ~2022 code predates removals in modern
   Python/scipy:
   - `collections.MutableMapping` alias (vendored `pint`, broken on Python ≥3.10).
   - `scipy.integrate.cumtrapz` → `cumulative_trapezoid` (a genuine drop-in).
   - `scipy.misc.derivative` → a central-difference stand-in (no drop-in exists;
     **not yet numerically validated** against callers).

Its unpinned, ~2022-vintage transitive deps (numpy/scipy/scikit-learn/matplotlib/
plotly) are exactly the kind of thing that will keep fighting an actively-updated
core dependency set. So SUAVE must **not** go into `pyproject.toml` / the shared
`uv` env.

## 2. Options

### Option 1 — Dedicated venv + a maintained `suave_compat` shim module (recommended)
- Keep SUAVE in its own venv (`--no-build-isolation` install), never `uv add`'d.
- Turn PR #33's exploration monkeypatches into a small, tested, well-commented
  `suave_compat` module in YAADO (e.g. `YAADO_Core/modules/suave_compat.py`) that
  the real (non-injected) `VehicleFactory` path imports **before** `import SUAVE`.
  SUAVE source stays untouched (pinned submodule).

Pros: minimal, keeps the fix versioned and tested instead of tribal knowledge.
Cons: the `derivative` shim's numerics must be validated before trusting any
SUAVE code path that calls it.

### Option 2 — Devcontainer / Docker image with SUAVE baked in
Ship a container (or devcontainer) that has the SUAVE venv + shims pre-built.

Pros: reproducible, hides the install pain entirely; good for CI and onboarding.
Cons: heavier infra; still needs the shim logic somewhere.

### Option 3 — Vendor patches into the submodule
Patch `external/suave` directly to fix the removed-API imports.

Pros: no runtime shims. Cons: means maintaining a **fork** of a pinned submodule —
rejected by the project's "don't edit pinned submodules" rule.

## 3. Recommendation

**Option 1 now, Option 2 later.** Add a tested `suave_compat` shim module and keep
SUAVE in a dedicated venv; move to a baked container when CI/onboarding demand it.
Two version pins should be chosen deliberately: pin the SUAVE venv's exact
scipy/numpy (not "latest"), and audit which SUAVE code paths YAADO actually calls
before trusting the `derivative` shim's numerics.

## 4. CI implication

The #29 SUAVE-gated integration test
(`test_build_with_real_suave_produces_real_vehicle`, currently `SKIPPED` in the
normal `uv run pytest` flow) needs a **separate CI job**:
1. check out the `external/suave` submodule;
2. build a dedicated venv with `--no-build-isolation` + the `suave_compat` shim
   pre-imported;
3. run only that gated test with that venv's interpreter — never the same one that
   runs the rest of the `uv run pytest` suite.

Until that shim module and job exist, the gated test staying `SKIPPED` in the shared
env is the correct, safe default — do **not** try to make SUAVE importable in the
project `uv` env.

## 5. Open questions

- `suave_compat` location: `YAADO_Core/modules/suave_compat.py`, or a top-level
  `tools/` / `integrations/` home (it is glue, not a physics module)?
- Container now, or defer until a real CI need?
- Who owns validating the `scipy.misc.derivative` replacement's numerics, and
  against which SUAVE call sites?
