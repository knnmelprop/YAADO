# RFC 0002 — Closing the ComponentStore gaps for physics-owned parameters

**Status:** Draft / Request for Comments
**Related:** #28 (analysis setup contract)

> An RFC is a design proposal circulated for team feedback *before* implementation.

## 1. Problem

#28 established that every solver reads its inputs from the validated
`BaseVehicleConfig` object. During that migration the delegated subagents found
that several solvers need parameters that **do not exist anywhere in the
ComponentStore schema**. Per #28's own rule (never fabricate a field), those
values were left sourced from `operating_state` overrides or module-level
constants rather than from the vehicle — which means #28's goal ("all vehicle
data is owned by the vehicle object") is only *partially* met.

This RFC proposes how to close those gaps deliberately, rather than letting
solver-local constants quietly become the source of truth.

## 2. Inventory of gaps (found during #28)

| Solver / module | Missing parameter(s) | Currently sourced from |
|---|---|---|
| `powerplant` inlet (`wedge.py`) | inlet-spike geometry: `cone_length_m`, `base_diameter_m`, `capture_area_m2`, `eta_diffuser` | `operating_state` / module constants |
| `powerplant` cycle (`mattingly.py`, `grzywka.py`) | combustor/nozzle losses: `pi_b`, `pi_cc`, `pi_nozzle`, `eta_b`, `h_PR`, gas `cp`/`gamma` | module placeholder constants |
| `wind_tunnel` XFOIL (`xfoil_runner.py`) | airfoil thickness / thickness-to-chord for fins | `FIN_THICKNESS_TO_CHORD` constant / `operating_state` |
| `stability_control` Barrowman | `AxisymmetricBody.nose_length_m`, `nose_diameter_m`; `Fins.chord_root_m`, `chord_tip_m` **are Optional but required** by the solver | solver raises `ValueError` if absent |
| `powerplant` cycle | `RamjetEngine.fuel_type` exists but is **unused** — `h_PR` is a hardcoded kerosene constant regardless of `fuel_type` | ignored |

## 3. Options

### Option 1 — Add flat fields to the existing components
E.g. add `capture_area_m2`, `cone_length_m` to `AxisymmetricBody`; `pi_b`, `h_PR`
to `RamjetEngine`; `thickness_to_chord` to `Fins`/`Wings`.

Pros: minimal, direct. Cons: bloats components with discipline-specific knobs;
mixes geometry with loss coefficients; harder to reuse across vehicles.

### Option 2 — Add small composable components (recommended)
Introduce focused, reusable schema bricks and attach them where relevant:
- `InletGeometry` (spike/cone geometry + `capture_area_m2`, `eta_diffuser`)
- `CombustorLosses` / `CycleLossCoefficients` (`pi_b`, `pi_cc`, `pi_nozzle`, `eta_b`, `h_PR`, `cp`, `gamma`)
- `AirfoilSection` (designation + `thickness_to_chord`) reused by `Wings`/`Fins`
- A fuel table mapping `fuel_type` → `h_PR` so the existing field is actually wired.

Pros: matches YAADO's "composition of Lego bricks" philosophy; discipline data
stays grouped and reusable; keeps core components lean. Cons: more schema surface
to design and validate.

### Option 3 — Formalize `operating_state` as the home for some of these
Some parameters (e.g. loss coefficients tuned per operating point) may genuinely
belong to `operating_state`, not the vehicle. This RFC should decide, per
parameter, whether it is a *vehicle property* or an *operating condition*.

## 4. Required-field question (Barrowman)

`AxisymmetricBody.nose_length_m` / `nose_diameter_m` and `Fins.chord_root_m` /
`chord_tip_m` are currently `Optional`, yet Barrowman cannot run without them.
Options: (a) make them required on the schema; (b) keep them optional but add a
model-level validator/precondition with a clear error (current behavior — the
solver raises `ValueError`); (c) provide documented physical defaults. Making
them required is the cleanest if every consumer needs them, but may over-constrain
vehicles that never run Barrowman — hence the composable-component route in
Option 2 (a body only carries a `NoseGeometry` brick when it needs one).

## 5. Recommendation

**Option 2 (composable components)** for the geometry/loss groups, plus wiring
`fuel_type → h_PR` via a small fuel table. For the Barrowman-required fields,
prefer per-consumer validation (b) over making everything required globally,
consistent with the composition philosophy. Classify each remaining parameter
explicitly as vehicle-owned vs operating-state before implementing.

## 6. Open questions

- Per parameter: vehicle property or operating condition?
- Do we want a general `AirfoilSection` brick now, or defer until a second
  consumer needs thickness?
- Should loss-coefficient defaults live in the schema (with validators) or in a
  named "reference engine" preset in `Hangar/`?
