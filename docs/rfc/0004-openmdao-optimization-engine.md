## 1. Problem & why now

YAADO is named an "MDO framework," but today it **analyzes** (geometry → CL/CD/thrust/mass) and
does not **optimize** (no design-variable → objective/constraint loop). `FlightDeck/README.md`
already declares the intended fix — a "Hidden OpenMDAO Engine" wrapping the analyses in an
optimization loop — but that vision was committed by a single contributor (`8339c88`) without
team sign-off, and FlightDeck is still an empty stub. OpenMDAO itself is **already a transitive
dependency** (`openmdao==3.45.0` via `om-pycycle`), so this is not a "adopt a new tool" decision;
it is a "ratify the mechanism and build the first slice" decision. Writing this RFC before
FlightDeck code exists is cheap; writing it after code accretes around unstated assumptions is not.

The **identity** question ("analysis vs optimization tool") is treated as already answered (CLAUDE.md
+ FlightDeck README). What this RFC decides is the **mechanism**.

## 2. Decisions this RFC must settle

1. **Loop target — direct vs SUAVE-mediated.** FlightDeck's README routes optimization *through*
   SUAVE's mission simulation. But SUAVE cannot go in the shared env (RFC 0003/#41 — needs a
   dedicated venv + shims). **Proposed:** first slice optimizes `BaseAnalysis` outputs **directly**
   (skip SUAVE routing) to de-risk against the unresolved isolation problem; SUAVE-in-the-loop
   becomes a later slice once #41 is resolved.
2. **The `BaseAnalysis → ExplicitComponent` adapter.** One generic adapter, not one per solver:
   ```python
   class BaseAnalysisComponent(om.ExplicitComponent):
       # inputs  ← selected BaseVehicleConfig design-variable fields
       # outputs ← selected AnalysisResults.data keys
       def compute(self, inputs, outputs):
           vehicle = self._vehicle.model_copy(update=_expand(inputs))
           self._analysis.setup(vehicle, self._operating_state)
           outputs.update(self._analysis.execute().data)
   ```
   This leans on the #28 uniform `setup(vehicle, operating_state)` contract (already merged).
3. **Design-variable mapping.** Pydantic `Field(ge=, le=)` bounds → `add_design_var(lower=, upper=)`.
   Needs a field-path ↔ flat-vector translation layer (Pydantic models are not native OM inputs);
   `model_copy(update=...)` per iteration.
4. **Derivative strategy (the hard part).** Subprocess solvers (AVL/XFOIL/SU2) expose no analytic
   Jacobians. **Proposed mixed strategy:** FD (`method='fd'`) around external-binary components;
   complex-step / hand-analytic around the pure-Python `LEVEL_0` correlations; gradient-free driver
   (`ScipyOptimizeDriver` COBYLA / a genetic/DOE driver) as the fallback where FD-around-CFD is too
   costly. SU2-in-the-loop by FD is likely prohibitive → that is where surrogates (deferred) enter.

## 3. Sub-parts (named here, not separately RFC'd)

- **Trajectory optimization via Dymos** (research R2). Dymos is collocation/optimal-control *on*
  OpenMDAO — the same engine, applied to trajectories. It would replace the shooting core of
  `flight_dynamics/point_mass_3dof.py` (`boost_dynamics` + `solve_ivp`) with a two-phase
  `Trajectory` (solid boost → ramjet cruise), turning fixed launch-angle / fixed-Mach cruise into
  an optimized `alpha(t)` / speed-altitude profile. Requires smoothing the `CD(Mach)` step and
  vectorizing the RHS; may need `pyoptsparse`/IPOPT. **Sequenced as the second slice of this RFC.**
- **Differentiable analytic methods** (research R3). Barrowman/Ackeret/DATCOM are scalar `math`;
  a `jnp` rewrite (~S each) plugs into OpenMDAO's native `JaxExplicitComponent` for exact partials.
  **Deferred to the slice where the loop actually needs gradients** — doing it earlier is an API
  with no consumer. Watch the non-smooth `CD`/Mach-branch derivative and JAX float32 default.
- **Surrogates over CFD** (research R4) are a *future consumer* of this loop, gated separately on a
  working SU2 pipeline — tracked as its own backlog item, not built here.

## 5. Risks

- FD-around-CFD cost may make L2/L3 modules impractical in-loop → may force gradient-free drivers
  or surrogates sooner than planned.
- Pydantic ↔ flat-design-vector translation is unexplored; no sketch exists yet.
- Overlap risk with whoever authored the FlightDeck README vision — coordinate before building.
- Student-audience usability (CLAUDE.md) vs OpenMDAO/Dymos learning curve — the complexity must
  stay hidden behind `BaseAnalysis`/FlightDeck, per the "user-friendly superstructure" rule.
