## 1. Streszczenie (Summary)

YAADO's public, Apache-2.0 repository currently ships one real CFD building block —
an inviscid-Euler SU2 `.cfg` generator (`su2_config_template.py`) — that is disconnected
from any working mesh-generation or solver-execution pipeline, and whose docstring still
names a specific vehicle ("ramjet rocket") and a pre-refactor module path, in the same
breath as the new generic "Generic Vehicle" terminology. This RFC recommends:

1. **SU2 becomes YAADO's first-class, publicly-supported CFD solver.** It is
   license-clean for a public Apache-2.0 repo (LGPL-2.1), purpose-built for aerospace/
   compressible flow, and — per new research below — already ships adjoint-based shape
   optimization infrastructure YAADO does not yet use.
2. **OpenFOAM becomes an optional, publicly-supported second choice**, for cases SU2 does
   not cover well, with `DAFoam` flagged as the concrete integration path if/when OpenFOAM-based
   MDO is wanted, rather than hand-writing an adjoint wrapper.
3. **PyFluent/Ansys Fluent is explicitly excluded from the public YAADO_Core.** Its
   academic license terms create real legal exposure for a public Apache-2.0 repository
   (see §3.4) that this RFC cannot resolve on its own authority. It may live as an
   optional, local-only integration inside a private, vehicle-specific repository (e.g.
   a future private `ramP`), never inside `YAADO_Core/` or any file this repository
   distributes.
4. **The 3D boundary-layer meshing gap is a known, structural limitation of the free
   tool stack**, not a bug to patch — see §4.2 for the concrete options and staged
   acceptance criteria this RFC proposes.
5. **RANS/viscous solver support and GCI studies are vehicle-specific work and belong in
   `Hangar/<vehicle>/analyses_private/`**, not in `YAADO_Core/`, consistent with the
   project's Core-stays-generic rule; `YAADO_Core` only ships the generic inviscid-Euler
   config machinery plus (proposed) a generic RANS config generator with no baked-in
   vehicle geometry.

### 2.2 Why this needs a strategy decision now, not per-PR ad-hoc choices

Three different CFD tools have three different license regimes, three different meshing
maturity levels, and (per the appendix research below) at least one of them — SU2 — has
substantial unused capability already sitting in the repo's dependency graph. Picking a
tool per-PR risks (a) accidentally shipping Ansys-encumbered automation in a public
repo, (b) duplicating adjoint/optimization infrastructure that already exists inside
SU2, and (c) conflating "YAADO_Core generic CFD scaffolding" with "one vehicle's private
CFD study," which the project's own layering rule (`YAADO_Core` never contains
vehicle-specific logic) already forbids conflating.

### 2.3 The internal-flow open question this RFC must acknowledge

A prior, unexecuted research thread in this project asked whether CFD for vehicles with
an active internal duct (e.g. a ramjet in `Hangar/`) should be **external-only** (a
blocked inlet), **internal-external coupled**, or an intermediate **mass-flow
inlet/outlet boundary condition**. This RFC does not resolve that question — it is
orthogonal to *which solver* and depends on vehicle-specific engineering judgment — but
notes it is **solver-relevant**: SU2 and OpenFOAM have different native support for
mass-flow BCs (see §4.4), so whichever answer that thread eventually reaches will narrow,
not widen, this RFC's solver choice. This RFC recommends the internal-flow-modeling
question be tracked as its own, separate RFC once someone picks it back up, informed by
§4.4 below rather than decided inside it.

## 3. Szczegółowy projekt (Detailed Design)

### 3.1 Directory structure decision

**Recommendation: add `YAADO_Core/modules/wind_tunnel/methods/openfoam/` for the
config-generation-only, mesh-execution-optional OpenFOAM path. Do NOT add
`YAADO_Core/modules/wind_tunnel/methods/pyfluent/` or any PyFluent-touching file
anywhere under `YAADO_Core/`.**

- `su2/` (existing) stays the first-class path: fixed (§3.2), de-RamP-ified (§3.3), and
  eventually extended with a generic RANS config path (§3.5).
  Every SU2 config generator here follows the existing `BaseAnalysis.setup(vehicle:
  BaseVehicleConfig, operating_state)` contract established by #28 — the same pattern
  `avl_wrapper.py`/`avl_builder.py` already use post-#28.
- `openfoam/` (new) hosts a generic `.foam`/case-directory generator analogous in scope
  to today's `su2_config_template.py`: it writes `rhoCentralFoam`/`sonicFoam` case
  dictionaries (`controlDict`, `fvSchemes`, `fvSolution`, boundary conditions) from a
  `BaseVehicleConfig`, with the same "writes files, does not itself invoke a binary
  unless the binary is verifiably present" discipline the SU2 module already documents
  (correctly) for itself. This keeps OpenFOAM at parity with SU2's current scope —
  neither gets a full owned pipeline in this RFC; both are config generators until §7
  scopes execution.
- **No `pyfluent/` directory, no PyFluent import, no PyFluent-authored `.cfg`/journal
  file generator anywhere in `YAADO_Core/` or `Hangar/` if `Hangar/` stays in this
  public repository.** See §3.4 for the reasoning and §7.4 for what remains genuinely
  unresolved.

### 3.2 SU2 as first-class solver — rationale

- **License**: LGPL-2.1, no redistribution or "competitive analysis" restrictions
  relevant to a public Apache-2.0 repo publishing config-generation code (not SU2's own
  source — SU2 itself is a separate, already-appropriately-licensed upstream project;
  YAADO only generates its input files).
- **Domain fit**: purpose-built for aerospace design; an academic source cited in this
  RFC's brief characterizes SU2 as offering a "variety of solvers for compressible
  cases" and being "simple to set up" relative to OpenFOAM specifically for compressible
  flow — the flight regime (Mach 0.8–3.0 per the existing `MACH_SWEEP`) every vehicle in
  `Hangar/` today actually flies in.
- **Already-present, unused capability** (new research, see Tool Research Appendix §6.1):
  SU2 ships `continuous_adjoint.py`, `discrete_adjoint.py`, and an orchestrating
  `shape_optimization.py` (SU2_CFD → SU2_CFD_AD → SU2_DOT_AD → geometry update loop) in
  its standard distribution — not a separate tool. This is directly relevant to the
  "analysis tool vs optimization tool" question already open in `docs/rfc/0004-openmdao-optimization-engine.md`:
  SU2-side shape optimization is available without building anything new, and `pysu2`
  (SU2 built with `-Denable-pywrapper=true`) offers a tighter, in-process integration
  path with an eventual OpenMDAO-driven `FlightDeck` loop than the current
  subprocess/`.cfg`-file pattern. **This RFC does not propose adopting `pysu2` or
  `shape_optimization.py` now** — that is RFC 0004's territory once FlightDeck exists —
  but flags it so RFC 0004's author does not have to rediscover it.

### 3.4 PyFluent / Ansys Fluent — legal analysis (the core blocker)

This is the section this RFC treats as load-bearing, and where it is most conservative
about not assuming a favorable reading.

**What is verified about Ansys academic licensing** (per the brief's cited research,
which this RFC did not independently re-verify against Ansys's current legal terms —
see §7.4):
1. Explicit prohibition on "competitive analysis (such as benchmarking)."
2. Prohibition on commercial use of any kind.
3. A geographic/institutional-affiliation restriction (commonly ~50 miles / 80 km from
   a "Designated Site") absent an extended license.
4. Critically: a **"Teaching" license — the tier most commonly available to students
   for free — explicitly may not be used for research or for publishing results.**

**Why this blocks PyFluent in `YAADO_Core`, independent of whether the club's specific
license is Teaching or Research:**

- YAADO is a **public**, Apache-2.0-licensed repository. Publishing PyFluent automation
  scripts there is *publishing*, in the plain-English sense the Teaching-license clause
  uses, regardless of whether simulation *results* are included. A public commit history
  containing a working `pyfluent` watertight-geometry + solve automation script is hard
  to distinguish, to a licensing reviewer, from "publishing research use of Fluent," even
  if narrowly it is "just code."
- Even under a Research-tier license (which lifts the no-research/no-publication
  restriction), the competitive-analysis and redistribution terms of Ansys's End User
  License Agreement are separate clauses this RFC's author cannot verify without reading
  the club's actual, current, signed license agreement — which no automated research
  pass has access to.
- The safe, defensible design is therefore: **treat "is this specific automation script,
  published in this specific public repo, compliant with our specific Ansys license" as
  a question only a human with the actual license text can answer — and default to
  "no" until they say otherwise.** This RFC does not attempt to pre-clear that answer.

**Where PyFluent may still live, if the answer eventually comes back favorable:**
Never inside `YAADO_Core/` (which this repository always distributes) and never inside
any part of the public `YAADO` repository, full stop. If a science-club project (e.g. a
private `ramP` fork/companion repo) has a verified, appropriate Ansys license and that
repository is **not** public, a local, optional PyFluent integration living entirely in
that private repository's own `analyses_private/` tree — never imported by, and never
imported into, `YAADO_Core` — is architecturally consistent with the existing
`Hangar/<vehicle>/` vs `YAADO_Core/` separation and does not require this RFC's
blessing, because it never touches the public repo this RFC governs. This RFC's only
claim about that scenario is: **it must never leak into `YAADO_Core/` or any file this
public repository ships**, and per §7.4, whether even *that* private use is licensed
appropriately remains something only the club's license-holder can confirm.

### 3.5 RANS/viscous + GCI study — where does it live?

**Recommendation: split by genericity, not by solver.**

- **Generic, vehicle-agnostic RANS config machinery** (turbulence-model selection
  boilerplate, a documented mesh-quality gate function, a documented GCI-study *driver*
  that takes N mesh-density configs and computes Richardson extrapolation / GCI from
  their outputs) is exactly the kind of "swappable physics solver" `YAADO_Core/modules/`
  already hosts for AVL/XFOIL — it belongs in `YAADO_Core/modules/wind_tunnel/methods/su2/`
  (and, if adopted, `openfoam/`), generic over `BaseVehicleConfig`, with zero
  vehicle-specific geometry or mesh files baked in.
- **A specific vehicle's actual mesh files, convergence study results, chosen mesh
  density, and any vehicle-specific viscous-correction tuning** belong in
  `Hangar/<vehicle>/analyses_private/` — this is vehicle-specific *data and results*,
  not swappable *method* code, and the project's own layering rule already says
  `YAADO_Core` must never encode vehicle-specific logic.
- This mirrors how `avl_wrapper.py`/`barrowman_stability.py` already separate generic
  solver code (`YAADO_Core/modules/`) from a vehicle's actual geometry (read from a
  validated `BaseVehicleConfig`, never hardcoded) — the same pattern applies to mesh
  density studies: the *driver* is generic, the *study results for vehicle X* are not.

### 3.6 Boundary-layer meshing — see §4.2 for the detailed options; this section states
the design consequence: **`YAADO_Core`'s generic mesh-generation helper (wherever it
ends up living — likely `airframe/slicer_methods/` per the existing module, extended)
must expose an explicit, queryable "boundary-layer mesh quality" flag/metadata field in
its output, not silently produce an isotropic tet mesh and let a downstream RANS run
silently use a bad y+ without anyone noticing.** This is a direct, actionable design
requirement this RFC adds regardless of which meshing option §4.2 eventually picks.

## 6. Tool Research Appendix

*(Preserved largely as supplied in the task brief, since it is independently sourced and
directly informs §3 and §5 above; lightly reformatted for this RFC's structure.)*

### 6.1 SU2 — beyond the config generator

SU2 ships adjoint-based shape-optimization infrastructure in its standard distribution,
unused by YAADO's current config-generator-only integration:
- **Continuous adjoint** (`continuous_adjoint.py`) and **discrete adjoint**
  (`discrete_adjoint.py`) are both part of the standard SU2 distribution, requiring no
  additional tool.
- **`shape_optimization.py`** orchestrates a full loop: SU2_CFD (solve) → SU2_CFD_AD
  (adjoint) → SU2_DOT_AD (gradient projection onto design variables) → geometry update →
  repeat, defaulting to `DISCRETE_ADJOINT`.
- **`pysu2`**: SU2 built with `-Denable-pywrapper=true` (meson) is importable as a Python
  module, not just a subprocess-invoked binary — a materially tighter integration path
  for a future OpenMDAO-driven `FlightDeck` loop than the current `.cfg`-file +
  subprocess pattern.

**Implication:** the infrastructure RFC 0004 discusses building for MDO already partly
exists inside SU2 and does not need to be re-invented — it needs discovering and wiring.

Sources (as supplied): SU2 execution docs (`su2code.github.io/docs_v7/Execution/`,
`su2code.github.io/docs/Execution/`), `shape_optimization.py` reference copies (MIT
Athena mirror, SU2 GitHub `current/bin`).

### 6.2 OpenFOAM — compressible solver family and a corroborated meshing limitation

- **`rhoCentralFoam`**: density-based, Kurganov-Tadmor central-upwind schemes, native
  shock-capturing support — the recommended solver for strong-shock regimes (e.g. an
  oblique shock off an inlet cone at Mach 2.5, directly in scope for `Hangar/` vehicles).
- **`sonicFoam`**: pressure-velocity (PIMPLE) solver for trans-/supersonic flow,
  semi-implicit; generally slower but can be more numerically stable than
  `rhoCentralFoam` in some configurations.

**Independently corroborated finding on boundary-layer meshing**: the prism/boundary-layer
generation problem the team hit in Gmsh is **not tool-specific** — it is a documented
limitation across the free meshing ecosystem. A thesis comparing `snappyHexMesh`,
`cfMesh`, and the commercial `HyperMesh CFD` on a real Formula-Student-car geometry
reports both free meshers **failing** to reach target prism-layer thickness, with only
the commercial tool succeeding. Independent CFD-Online community discussion corroborates
the same specific failure modes ("Prism layers are really bad... hard to achieve without
the BL collapsing" for `snappyHexMesh`; "Prism layer thickness and transition control is
really bad" for `cfMesh`).

**Implication for this RFC:** this is a **structural limitation of the free tool stack**,
not a bug awaiting a patch. §4.2/§3.6 above already build this in as a design
requirement (explicit mesh-quality flagging) rather than a promise to "just fix Gmsh."

Sources (as supplied): OpenFOAM compressible-solver docs (`openfoam.com` API/user-guide
pages, multiple versions), EPJ Web of Conferences comparison paper (`rhoCentralFoam` vs
`sonicFoam`), the HAW Hamburg thesis (`opus4.kobv.de`) comparing free vs. commercial
mesh tools, CFD-Online forum thread on open-source meshing tool pros/cons.

### 6.3 DAFoam — new finding, directly relevant to the "optimization tool" question

**DAFoam** (Discrete Adjoint with OpenFOAM) is an existing, mature open-source framework
that already does what an earlier, separate research thread (RFC 0004 / the
"analysis vs optimization tool" discussion) treated as an open, unbuilt direction:

- Implements discrete adjoint for any steady-state OpenFOAM solver, reportedly adding
  only "a few hundred lines" over the standard solver.
- Ships a ready **Python interface to OpenMDAO** — directly relevant since OpenMDAO is
  already a transitive YAADO dependency via `pyCycle` (per RFC 0004's research).
- Supports multidisciplinary optimization beyond pure aero (heat transfer, structures,
  hydrodynamics, radiation).

**Implication:** if OpenFOAM-based MDO is ever pursued, DAFoam is the concrete adoption
path (a vendored submodule alongside `external/su2`, `external/pycycle`), not a wrapper
to be hand-built. This directly informs RFC 0004's future scope, not just this RFC's.

Sources (as supplied): DAFoam GitHub repo/README, DAFoam ReadTheDocs, He et al.
(University of Michigan MDO Lab) DAFoam paper PDF.

### 6.4 PyFluent — Watertight Geometry workflow and its input-geometry precondition

PyFluent's scriptable "Watertight Geometry" meshing workflow is well-documented and
fully automatable in Python (example snippet supplied in the brief, using
`meshing.watertight()`, `create_surface_mesh`, `create_volume_mesh_wtm`, etc.).

**Critical caveat directly relevant to this repo's actual geometry pipeline**: this
workflow explicitly assumes geometry already prepared as "watertight" in a CAD tool such
as Ansys SpaceClaim. A raw STEP export from typical design tools is not watertight by
default, and this project's own prior geometry work (referenced in the brief as PR #13)
found real topological issues (nested solids, ambiguous openings) in exactly this kind of
raw geometry — meaning a PyFluent path would additionally require either SpaceClaim
(another Ansys license) or manual cleanup in Gmsh/FreeCAD before PyFluent could even
start, on top of the licensing blocker in §3.4.

Sources (as supplied): PyFluent meshing-workflows docs and cheat sheet
(`fluent.docs.pyansys.com`), PyFluent CHT example, legacy/classic meshing workflow docs.

## 7. Wady / ryzyka (Drawbacks & Risks)

- **Adding `openfoam/` doubles the config-generator surface area to maintain** without

brief (newer Gmsh, SU2-native meshing, Fluent Meshing) but none was conclusively
validated by this RFC. **Someone with a working Gmsh/SU2 environment needs to actually
test** whether a newer Gmsh release adds a 3D OCC-kernel anisotropic prism-layer

chosen fix with a timeline."

consequential open question in this RFC. **Whoever is responsible for the science club's

**§7.6 — Internal-flow boundary-condition strategy for ducted vehicles.** As noted in

ramjet-type vehicles; it only notes that whichever solver this RFC's readers pick should
